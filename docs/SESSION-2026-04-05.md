## Task 1: Compare Tab — Database Dropdowns

### Problem
The Compare tab currently treats connections as atomic server+database pairs. There's no way to switch databases without going back to Connection Manager and creating a separate connection entry. Every other SQL IDE lets you pick a server, then pick a database on that server.

### What to Build
Add a database dropdown next to each connection indicator (Source, Target 1, Target 2) on the Compare tab toolbar.

**Behavior:**
- When a connection is selected (or restored on startup), query `sys.databases` on that server and populate the dropdown
- Auto-select the database from the `SavedConnection.Database` field as the default
- If there's only one user database, just select it — don't make the user click
- When the user changes the database dropdown, rebuild `_sourceConnectionString` / `_targetConnectionString` with the new `InitialCatalog` and re-trigger the comparison
- If no connection is selected, the dropdown is hidden
- If connection disconnects, hide the dropdown

**Layout placement — this is critical:**
- Source connection is LEFT-aligned → database dropdown goes to the RIGHT of the ConnectionIndicator (inward, toward center)
- Target 1 connection is RIGHT-aligned → database dropdown goes to the LEFT of the ConnectionIndicator (inward, toward center)
- Target 2 connection is RIGHT-aligned → database dropdown goes to the LEFT of the ConnectionIndicator (inward, toward center)
- The connection indicator itself does NOT move. The dropdown is added next to it on the inner side.

**Current layout reference** (`CompareView.axaml`):
```
Row 0: [Source: ●indicator] [⇄] [Code|Tables|Data] [Search...] [Target1: ●indicator] [+Target2]
Row 1: (conditional)                                              [Target2: ●indicator]
```

After change:
```
Row 0: [Source: ●indicator] [DB▾] [⇄] [Code|Tables|Data] [Search...] [DB▾] [Target1: ●indicator] [+Target2]
Row 1: (conditional)                                        [DB▾] [Target2: ●indicator]
```

**Implementation notes:**
- The Editor tab already has a working database dropdown (`QueryTabView.axaml`) — reference that pattern for loading databases and styling
- The dropdown should use the same compact styling as the Editor's database picker
- Database list should filter out system databases (master, model, msdb, tempdb) by default — same as Object Explorer does
- Connection string rebuild: use `SqlConnectionStringBuilder` to swap `InitialCatalog`, don't string-replace
- Wire `SelectionChanged` to re-run `LoadObjectsAsync()` so the object list refreshes with the new database
- Add `SourceDatabases`, `TargetDatabases`, `Target2Databases` as `ObservableCollection<string>` on CompareViewModel
- Add `SelectedSourceDatabase`, `SelectedTargetDatabase`, `SelectedTarget2Database` as `[ObservableProperty]` strings

## Task 2: Results Grid — Cell/Row Selection Visual Bug

### Problem
In the query results DataGrid, when you click a cell and drag down to select a range, the visual feedback shows entire rows highlighted (as if row-selection mode). But the actual selection is correct — pressing Cmd+C copies only the focused column's values from the selected rows. The visuals are lying about what's selected.

This is an Avalonia DataGrid limitation. The DataGrid's built-in selection rendering highlights full rows regardless of `SelectionUnit` setting. We tried fixing this before and it didn't stick.

### What to Build
Fix the visual selection so that when a user clicks a cell and drags down a column, only that column's cells appear selected — not the entire rows.

**Expected behavior:**
- Click cell → that cell highlights
- Click + drag down in same column → those cells in that column highlight
- Shift+click on another row → same column, range of cells highlight
- Cmd+C copies the focused column values from all selected rows (this already works)
- Full row selection (clicking row header or Shift+Click without a cell focus) should still highlight the full row

**Investigation hints:**
- Avalonia's DataGrid paints row-level selection backgrounds via `DataGridRow` styles. The `SelectionUnit="Cell"` property exists but the visual rendering still uses row-level brushes.
- Possible approach: override the row selection background to transparent when `SelectionUnit="Cell"`, and instead apply cell-level backgrounds via `DataGridCell` styles or a custom `LoadingRow` handler that checks `cell.IsSelected`.
- Another approach: use `CellPointerPressed` / `CellPointerMoved` events to manually manage a visual overlay or per-cell background, separate from the DataGrid's built-in selection model.
- The existing multi-cell copy logic (v2.11.0) already tracks which column is focused — that same column index can drive the visual highlighting.
- Check `QueryTabView.Results.cs` (or whichever partial handles the results grid) for the current copy logic to understand how column focus is tracked.

**Constraints:**
- Don't break existing features: row selection, Cmd+C copy, multi-cell copy, edit mode, stacked results
- Must work in both dark and light themes (use DynamicResource for any selection colors)
- Performance matters — results can have thousands of rows, so per-cell style recalculation needs to be efficient

## Task 3: History Tab — Empty State & Feedback UX

### Problem
The History tab has terrible first-run UX. When you land on it without DDL audit configured:

1. **No prominent guidance**: The "Version tracking: not configured" message is tiny text in the top-right corner and status bar. It blends into the UI completely. The user has to click Sync to discover they need to set something up — by which point they've already wasted time.

2. **Interactive controls are live but useless**: The database dropdown, search box, Object Browser, and Recent Changes grid are all fully interactive even though there's no data source configured. The user can type in search, select databases, and get zero feedback about why nothing happens. These controls should either be disabled or hidden behind the empty state.

3. **No loading/connection feedback**: When selecting a database from the dropdown, there's no indication of whether it's connecting, loading, or failing silently. The user has no idea if something is happening.

### What to Build

**Prominent empty state overlay** when DDL audit is not configured:
- Big centered message over the main content area (Object Browser + Recent Changes + Diff View), same pattern as the Compare tab's empty state overlay
- Text: "Version History requires a DDL audit trigger" with a brief explanation
- "Configure in Settings" button that opens Settings dialog directly to the Version History section
- The toolbar (connection, database dropdown, search, Sync, Refresh) should be visible but dimmed/disabled until configured

**After DDL audit IS configured but no data yet:**
- Show "No changes recorded yet. Click Sync to pull changes from the audit log." in the Recent Changes area
- Sync button should be visually prominent (primary style) to guide the user

**Loading feedback:**
- When Sync is clicked, show a spinner or progress indicator
- When database is changed, show brief loading state while objects refresh
- If connection fails, show the error inline — don't fail silently

**Reference:** The Compare tab already has an empty state overlay pattern (`ShowCompareOverlay` / `CompareOverlayMessage` in CompareViewModel). Reuse that same visual approach for consistency.

## Task 4: Settings — Admin / Normal User Mode

### Problem
Settings currently exposes everything to everyone: DDL trigger configuration, Git Export, audit table source — all DBA/admin concerns that confuse normal users. A developer or analyst opening Lookout for the first time shouldn't be confronted with "configure your DDL audit trigger." That's how we got the History tab confusion above.

### What to Build
Add a **User Type** toggle in Settings: **Normal** (default) and **Admin**.

**When Normal (default):**
- Hide DDL trigger setup section in Settings
- Hide Git Export section in Settings
- Hide DDL audit source configuration
- File → Export to Git menu item is hidden

**When Admin:**
- Everything visible as it is today
- DDL trigger setup, Git Export config, audit table source all accessible
- File → Export to Git visible

**Implementation notes:**
- Add `UserMode` enum (`Normal`, `Admin`) and `UserMode` property to `AppSettings`
- Default to `Normal`
- The toggle should be at the TOP of Settings, before any other sections — it controls what's visible below it
- Switching from Normal → Admin reveals the hidden sections immediately (no dialog restart)
- Switching from Admin → Normal hides them immediately
- Persist to settings.json
- This does NOT affect functionality — if an admin has configured Git Export and then switches to Normal mode, Git Export still runs on its schedule. It just hides the configuration UI.
