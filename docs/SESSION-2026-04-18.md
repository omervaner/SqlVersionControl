### Task 1: Pause Background Pollers When Tab/Window Inactive + Status Bar Indicator

**What we have today (verified in code):**

The polling landscape is small — only two places start a continuous timer:

1. **`ViewModels/ActivityViewModel.cs`** — `_autoRefreshTimer` (DispatcherTimer). Default interval 5 seconds. Started via `StartAutoRefresh()` when `AutoRefreshEnabled` property flips true. The timer's tick handler calls `RefreshAsync()` which runs DMV queries every tick (sessions OR jobs depending on sub-tab, plus `UpdateStatCardsAsync` which runs `GetServerHealthAsync` — another multi-DMV round-trip).
2. **`ViewModels/TraceViewModel.cs`** — `_counterTimer` (System.Threading.Timer). 3-second initial delay, 5-second period. Active only while `State == Recording`. Calls `ReadEventsAsync` against the XE session's ring buffer every tick.

There are NO other continuous pollers in the codebase. The folding timer in `QueryTabView.Editor.cs` is one-shot (`Timeout.Infinite` period), fires 500ms after the last text change. The rest is event-driven.

**So the energy drain is almost certainly Ömer having Auto-Refresh turned on in the Activity tab.** Once on, `_autoRefreshTimer` keeps firing every 5 seconds regardless of which main tab is active, whether the window is focused, or whether the app is backgrounded. Eight-hour day = ~5,800 DMV round-trips. That's the "significant energy" flag.

**The architectural fix — `BackgroundPollManager`:**

Build one service in `Services/BackgroundPollManager.cs` that every poller registers with. The manager gates tick execution on two signals:

- `bool IsWindowFocused` — updated from `MainWindow.Activated` / `MainWindow.Deactivated`
- `string? ActiveMainTab` — updated whenever the main tab selection changes (currently Editor / History / Compare / Activity / Trace / Settings)

A poller declares which tab it belongs to at registration. On each tick attempt, the manager runs the handler only if `IsWindowFocused && poller.OwningTab == ActiveMainTab` (or if the poller opted out of tab gating — the Trace XE reader might want to keep running server-side even when the tab isn't visible; see below).

Register each timer through the manager instead of spinning up its own `DispatcherTimer` / `System.Threading.Timer`. `ActivityViewModel.StartAutoRefresh` becomes a call to `pollManager.Register(owningTab: "Activity", interval: TimeSpan.FromSeconds(AutoRefreshIntervalSeconds), tick: RefreshAsync)`. The manager owns the timer.

**On tab activation, fire an immediate refresh THEN resume the periodic tick.** Don't leave the user staring at stale DMV numbers for 5 seconds after switching back to Activity. This is the "catch-up, not stale" behavior — the manager should expose `ResumePoller(id)` that does exactly this.

**Trace edge case:** Trace has a subtlety — stopping the `_counterTimer` locally doesn't stop the XE session server-side. The ring buffer keeps filling. So for Trace, the gating should pause the *local UI update* but leave the XE session running. When the user comes back to the Trace tab, do a catch-up read that drains whatever accumulated in the ring buffer. This needs a flag on the poller registration: `pauseServerSideOnTabInactive: false` (Trace) vs `true` (Activity, where there's nothing server-side to pause).

**Window focus behavior:** When the window loses focus, ALL pollers pause, period. No exceptions. This is what lets macOS App Nap engage.

**Status bar telemetry indicator:**

Small indicator on the right side of the status bar (`Views/MainWindow.StatusBar.cs`). Three states, event-driven — updates only when the `BackgroundPollManager` fires a state-change event:

1. **Idle** — dim dot + "idle" label. Shows when no pollers are currently ticking (window unfocused, tab inactive, or nothing registered).
2. **Polling** — small colored dot (reuse `AccentBlue` or `AccentGreen`) + label showing which category ("Activity", "Trace"). If multiple pollers active, show the highest-cost one or just "polling".
3. **Long-running op** — different dot + label ("query running", "export 42%"). Optional — this overlaps with the existing elapsed-time tab title indicator, so skip it for now to avoid duplicate UI.

Do NOT make this indicator update on a timer. It listens to `BackgroundPollManager.StateChanged` events, which fire only on actual transitions (window focus, tab change, poller start/stop). A handful of events per session — no measurable cost.

The indicator doubles as a debug view: if the user reports energy issues, they can check the indicator while the window is backgrounded. If it says "polling" while unfocused, the focus gating layer broke.

**Files:**
- NEW: `Services/BackgroundPollManager.cs` — the manager
- `ViewModels/ActivityViewModel.cs` — replace `StartAutoRefresh` / `StopAutoRefresh` / `_autoRefreshTimer` with manager registration; `OnAutoRefreshEnabledChanged` calls `pollManager.SetPollerEnabled(...)` instead
- `ViewModels/TraceViewModel.cs` — replace `_counterTimer` with manager registration using the `pauseServerSideOnTabInactive: false` flag
- `Views/MainWindow.axaml.cs` — wire `Activated`/`Deactivated` → manager; hook into the main tab selection change (whatever event drives `Editor`/`History`/`Compare`/`Activity`/`Trace`/`Settings` switching) → manager
- `Views/MainWindow.StatusBar.cs` — add the indicator control, subscribe to `BackgroundPollManager.StateChanged`
- `Styles/AppTheme.axaml` + `AppThemeLight.axaml` — add `PollIdleBrush`, `PollActiveBrush` resources (DynamicResource per the #4 rule)

**Verification:**

- Turn on Auto-Refresh, leave Activity tab, switch to Editor. Status bar indicator → "idle" within one tick interval. Activity DMV queries stop firing (check via server-side trace or a log statement in `RefreshAsync`).
- Cmd+Tab away. Indicator → "idle". macOS Activity Monitor should show Lookout's energy impact drop to near zero within ~30 seconds (App Nap engaging).
- Cmd+Tab back, tap Activity tab. Immediate refresh fires (the catch-up). Then periodic ticks resume.
- Start a Trace, switch to Editor. Local UI counter stops updating. XE session on the server is still running (verify with `SELECT * FROM sys.dm_xe_sessions`). Switch back to Trace — counter catches up.

**Main risk:** Getting the catch-up-on-resume right without double-firing (one on resume, another when the periodic tick hits immediately after). Solution: on resume, fire the tick manually AND reset the DispatcherTimer's next-tick clock so it's one full interval from now.

### Task 2: Editor Rectangle Selection Crashes on Option+Shift+Drag

**The crash (v2.14.2, 2026-04-18 17:23):**

```
Exception: AvaloniaEdit.Rendering.VisualLinesInvalidException
  at AvaloniaEdit.Rendering.TextView.get_VisualLines()
  at AvaloniaEdit.Rendering.BackgroundGeometryBuilder.GetRectsForSegmentImpl(...)+MoveNext()
  at AvaloniaEdit.Rendering.BackgroundGeometryBuilder.AddSegment(...)
  at AvaloniaEdit.Editing.SelectionLayer.Render(DrawingContext drawingContext)
```

**Root cause — found in code:**

`Views/QueryTabView.Editor.cs`, inside `ConfigureEditor()`:

```csharp
SqlEditor.TextArea.SelectionChanged += (_, _) => UpdateOccurrenceHighlight();
SqlEditor.TextArea.Caret.PositionChanged += (_, _) => UpdateOccurrenceHighlight();
...
SqlEditor.TextArea.Caret.PositionChanged += (_, _) => UpdateBracketHighlight();
```

And both `UpdateOccurrenceHighlight()` and `UpdateBracketHighlight()` end with:

```csharp
SqlEditor.TextArea.TextView.Redraw();
```

`TextView.Redraw()` is the nuclear option — it **invalidates all visual lines** and forces a full rebuild on the next render pass.

**The race during Option+Shift+drag:**

1. AvaloniaEdit's rectangle selection kicks in (assuming it's enabled — see below). Each pointer-move tick fires `Caret.PositionChanged` and `SelectionChanged`.
2. Our handlers fire → `UpdateOccurrenceHighlight()` calls `TextView.Redraw()` → visual lines marked invalid.
3. In the same or next composition frame, AvaloniaEdit's `SelectionLayer.Render()` is called to draw the rectangle overlay.
4. `SelectionLayer` computes geometry per segment via `BackgroundGeometryBuilder.GetRectsForSegmentImpl()`, which reads `TextView.VisualLines`.
5. `VisualLines` property throws `VisualLinesInvalidException` because step 2 invalidated them and they haven't been rebuilt.

Rectangle selection is especially exposed because it has N segments (one per covered line) instead of one — N opportunities for the race to hit. Regular text selection has a single contiguous segment and the race is effectively impossible to hit in practice.

Note: the three `DocumentColorizingTransformer` subclasses in `Rendering/` (Occurrence, Bracket, ExecutionFlash) are NOT themselves the problem — they're passive colorizers that only run during the visual-line build pipeline. The problem is the `TextView.Redraw()` calls in `QueryTabView.Editor.cs` that drive them.

**The fix — two parts:**

**Part A — stop over-redrawing.** Both handlers call `Redraw()` unconditionally on every caret/selection change. Guard them so they only redraw when the relevant state actually changed:

```csharp
// UpdateOccurrenceHighlight
var newWord = /* compute as today */;
if (_occurrenceHighlighter.SelectedWord == newWord) return;  // no change, no redraw
_occurrenceHighlighter.SelectedWord = newWord;
SqlEditor.TextArea.TextView.Redraw();
```

Same pattern in `UpdateBracketHighlight` — skip the Redraw if `OpenOffset` and `CloseOffset` are unchanged from last call.

This eliminates the vast majority of Redraws during a rectangle drag (the word/bracket state usually doesn't change while dragging a rectangle across blank space or the same line run). The race becomes very rare.

**Part B — downgrade `Redraw()` to a lighter invalidation.** `TextView.Redraw()` invalidates visual lines. `TextView.InvalidateVisual()` schedules a repaint without dumping the visual-line cache. Since `DocumentColorizingTransformer`-produced highlights ARE applied during visual line construction, `InvalidateVisual` alone won't re-run colorization. However, `TextView.Redraw(DocumentLine)` (single-line variant) or `TextView.Redraw(int startOffset, int length)` (range variant) only invalidates the affected lines — far less impact than the parameterless `Redraw()` which invalidates everything.

For `UpdateBracketHighlight`: only the two bracket lines need re-colorization. Call `Redraw(openLine)` and `Redraw(closeLine)` instead of the whole-view `Redraw()`.

For `UpdateOccurrenceHighlight`: in principle every visible line could need re-colorization. This is harder to localize. Acceptable compromise: keep the whole-view `Redraw()` here but rely on Part A's guard to make sure it only fires when SelectedWord actually changed.

Part A alone is probably sufficient in practice. Part B is the belt-and-suspenders fix if A doesn't fully eliminate the race.

**Part C — verify rectangle selection is actually enabled, and check modifier combo:**

Before fixing the crash, confirm the feature is even supposed to work. I searched the codebase — `RectangleSelection`, `EnableRectangularSelection`, `MouseSelectionMode` are NOT mentioned anywhere. That means we're relying on AvaloniaEdit's defaults.

AvaloniaEdit 11.3.0 defaults: rectangle selection exists as a feature, but whether it's enabled by default and what modifier triggers it has varied across versions. Ömer reports Alt+drag (Option+drag on macOS) does NOT create a rectangle selection — only extends text selection word-by-word. Alt+Shift+drag is the one that crashes.

So the state needs to be established empirically before fixing:

1. With crash-prevention applied (Part A), test Alt+drag. If it does rectangle selection, great — just document that Alt+Shift+drag isn't needed. If it still does nothing, the feature is either disabled or requires a different modifier.
2. If Alt+drag does nothing, try explicitly setting `SqlEditor.TextArea.RightClickMovesCaret = true` and look for any `SetRectangularSelection` API in AvaloniaEdit 11.3.0. Check release notes between 11.2 and 11.3 for MouseSelectionMode changes.
3. If needed, wire an explicit Alt+drag → rectangle selection handler in `ConfigureEditor` that calls `AvaloniaEdit.Editing.RectangleSelection.PerformRectangularPaste` / constructs a RectangleSelection directly.

This investigation has to happen before declaring Task 2 done.

**Files:**
- `Views/QueryTabView.Editor.cs` — `UpdateOccurrenceHighlight`, `UpdateBracketHighlight` (guards + lighter Redraw variant)
- Possibly `SqlVersionControl.csproj` — if the AvaloniaEdit 11.3.x patch bump resolves the modifier issue, bump it
- No changes needed in `Rendering/*.cs` — the transformers themselves are fine

**Verification:**
- Option+Shift+drag across a multi-line SELECT query 20 times without crash
- Confirm rectangle selection actually renders (selected cells should form a rectangle, not word-by-word extension)
- Occurrence highlight still works when double-clicking a word in normal usage
- Bracket highlight still works when caret is adjacent to `(` or `)`

### Task 3: Row-Header Selection + Cmd+C Copies Only One Column

**The bug — exact location:**

`Views/QueryTabView.EditMode.cs`, `OnResultsGridKeyDown()`, the `Cmd+C` branch. Current code:

```csharp
int minCol, maxCol;
if (_dragStartColIndex >= 0 && _dragEndColIndex >= 0)
{
    minCol = Math.Min(_dragStartColIndex, _dragEndColIndex);
    maxCol = Math.Max(_dragStartColIndex, _dragEndColIndex);
}
else if (grid.CurrentColumn != null)
{
    minCol = maxCol = grid.Columns.IndexOf(grid.CurrentColumn);
}
else if (_fullRowSelectionMode)
{
    minCol = 0;
    maxCol = grid.Columns.Count - 1;
}
else
{
    minCol = maxCol = -1;
}
```

**The branch order is wrong.** When the user clicks a row header:
- `OnRowHeaderPointerPressed` (in `QueryTabView.Results.cs`) correctly sets `_fullRowSelectionMode = true`
- But `grid.CurrentColumn` is not cleared — it's whatever column was last focused (hence the "FirstName" symptom: it's whichever column had focus before the row-header click, which happens to be FirstName in Ömer's repro)
- `_dragStartColIndex` / `_dragEndColIndex` stay at -1 (no drag happened)

So the Cmd+C handler falls into the `grid.CurrentColumn != null` branch first, never reaching the `_fullRowSelectionMode` branch below it. Dead code.

**The fix — reorder the branches so intent-first wins:**

```csharp
int minCol, maxCol;
if (_fullRowSelectionMode)
{
    // Full-row selection from row-header click: copy all columns
    minCol = 0;
    maxCol = grid.Columns.Count - 1;
}
else if (_dragStartColIndex >= 0 && _dragEndColIndex >= 0)
{
    minCol = Math.Min(_dragStartColIndex, _dragEndColIndex);
    maxCol = Math.Max(_dragStartColIndex, _dragEndColIndex);
}
else if (grid.CurrentColumn != null)
{
    minCol = maxCol = grid.Columns.IndexOf(grid.CurrentColumn);
}
else
{
    minCol = maxCol = -1;
}
```

That's it. One reorder.

**Also check:** `CopyWithHeadersAsync()` in `QueryTabView.Export.cs` already gets this right — it checks `_fullRowSelectionMode` first (sort of — it's folded into the else branch via `!_fullRowSelectionMode && _activeResultsGrid?.CurrentColumn != null`). That's why Copy with Headers works correctly but plain Cmd+C doesn't. Consistency point.

**Single source of truth note:** There are now THREE places computing column range for copy:
1. `OnResultsGridKeyDown` Cmd+C branch (EditMode.cs)
2. `CopyWithHeadersAsync` (Export.cs)
3. `RepaintCellSelection` + `ApplyCellSelectionToRow` (Results.cs) — for rendering

All four use the same logic shape but written out four times. This is exactly the #1 rule violation from CLAUDE.md. While fixing Task 3, factor the column-range resolution into a shared helper:

```csharp
private (int minCol, int maxCol) ResolveCopyColumnRange(DataGrid grid, int totalColumns)
{
    if (_fullRowSelectionMode)
        return (0, totalColumns - 1);
    if (_dragStartColIndex >= 0 && _dragEndColIndex >= 0)
        return (Math.Min(_dragStartColIndex, _dragEndColIndex),
                Math.Max(_dragStartColIndex, _dragEndColIndex));
    if (grid.CurrentColumn != null)
    {
        var idx = grid.Columns.IndexOf(grid.CurrentColumn);
        return (idx, idx);
    }
    return (-1, -1);
}
```

Then `OnResultsGridKeyDown`, `CopyWithHeadersAsync`, and the render paths all call it. Next time this logic needs to change, it changes in exactly one place.

**Files:**
- `Views/QueryTabView.EditMode.cs` — reorder Cmd+C branches
- `Views/QueryTabView.Export.cs` — refactor `CopyWithHeadersAsync` to use the shared helper
- `Views/QueryTabView.Results.cs` — refactor `RepaintCellSelection` / `ApplyCellSelectionToRow` to use the shared helper (these have the same shape with `-1` meaning "all columns" — keep that quirk if it's used)

**Verification:**
- Click a row header, Cmd+C, paste into Excel → all columns populate across row
- Shift+click two row headers, Cmd+C, paste → N rows × all columns
- Existing behaviors that must NOT regress:
  - Single cell click + Cmd+C → one cell value
  - Drag-select a 3×3 rectangle + Cmd+C → 3×3 region
  - Multi-row selection in a specific column via shift-click → Cmd+C copies that column only (the v2.11.0 behavior)

### Task 4: Right-Click "Copy" Copies Headers (Should Be Data Only)

**The bug — one line:**

`Views/QueryTabView.Export.cs`, `CopySelectedRowsAsync()`:

```csharp
var sb = new StringBuilder();
sb.AppendLine(string.Join("\t", result.ColumnNames));   // ← BUG: unconditional header line
foreach (var row in rows)
{
    sb.AppendLine(string.Join("\t", row.Select(v => v?.ToString() ?? "NULL")));
}
```

This method is wired to the "Copy Row" menu item in `SetupReadOnlyContextMenu`. The header prepend is unconditional — so "Copy Row" produces identical output to "Copy with Headers". Classic one-line oversight.

**The fix:** Delete the first `AppendLine` call. That's the entire fix.

```csharp
var sb = new StringBuilder();
foreach (var row in rows)
{
    sb.AppendLine(string.Join("\t", row.Select(v => v?.ToString() ?? "NULL")));
}
```

**Verification:**
- Right-click a row in results, "Copy" → paste → just values, one line per row, no header line
- Right-click, "Copy with Headers" → paste → header line present, then values (unchanged behavior)
- Both selections (single row, multi-row) behave correctly for both menu items

**While you're in this file:** `CopySelectedRowsAsync` is another candidate to share a helper with `CopyWithHeadersAsync`. Both serialize rows to TSV. A single `SerializeRowsAsTsv(rows, result, includeHeaders, minCol, maxCol)` helper kills the duplication. Same #1 rule reasoning as Task 3. Not required for this task — but worth doing the next time either method needs to change.
