### Task 1: Pause Background Pollers When Tab/Window Inactive + Status Bar Indicator

**What we have today (verified in code):**

The polling landscape is small — only two places start a continuous timer:

1. **`ViewModels/ActivityViewModel.cs`** — `_autoRefreshTimer` (DispatcherTimer). Default interval 5 seconds. Started via `StartAutoRefresh()` when `AutoRefreshEnabled` property flips true. The timer's tick handler calls `RefreshAsync()` which runs DMV queries every tick (sessions OR jobs depending on sub-tab, plus `UpdateStatCardsAsync` which runs `GetServerHealthAsync` — another multi-DMV round-trip).
2. **`ViewModels/TraceViewModel.cs`** — `_counterTimer` (System.Threading.Timer). 3-second initial delay, 5-second period. Active only while `State == Recording`. Calls `ReadEventsAsync` against the XE session's ring buffer every tick.

There are NO other continuous pollers in the codebase. The folding timer in `QueryTabView.Editor.cs` is one-shot (`Timeout.Infinite` period), fires 500ms after the last text change. The rest is event-driven.

**So the energy drain is almost certainly Ömer having Auto-Refresh turned on in the Activity tab.** Once on, `_autoRefreshTimer` keeps firing every 5 seconds regardless of which main tab is active, whether the window is focused, or whether the app is backgrounded. Eight-hour day = ~5,800 DMV round-trips. That's the "significant energy" flag.

**The architectural fix — `BackgroundPollManager`:**

Build one service in `Services/BackgroundPollManager.cs` that every poller registers with. The manager gates tick execution on two signals:

- `bool IsWindowFocused` — updated from `MainWindow.Activated` / `MainWindow.Deactivated`
- `string? ActiveMainTab` — updated whenever the main tab selection changes (currently Editor / History / Compare / Activity / Trace / Settings)

A poller declares which tab it belongs to at registration. On each tick attempt, the manager runs the handler only if `IsWindowFocused && poller.OwningTab == ActiveMainTab` (or if the poller opted out of tab gating — the Trace XE reader might want to keep running server-side even when the tab isn't visible; see below).

Register each timer through the manager instead of spinning up its own `DispatcherTimer` / `System.Threading.Timer`. `ActivityViewModel.StartAutoRefresh` becomes a call to `pollManager.Register(owningTab: "Activity", interval: TimeSpan.FromSeconds(AutoRefreshIntervalSeconds), tick: RefreshAsync)`. The manager owns the timer.

**On tab activation, fire an immediate refresh THEN resume the periodic tick.** Don't leave the user staring at stale DMV numbers for 5 seconds after switching back to Activity. This is the "catch-up, not stale" behavior — the manager should expose `ResumePoller(id)` that does exactly this.

**Trace edge case:** Trace has a subtlety — stopping the `_counterTimer` locally doesn't stop the XE session server-side. The ring buffer keeps filling. So for Trace, the gating should pause the *local UI update* but leave the XE session running. When the user comes back to the Trace tab, do a catch-up read that drains whatever accumulated in the ring buffer. This needs a flag on the poller registration: `pauseServerSideOnTabInactive: false` (Trace) vs `true` (Activity, where there's nothing server-side to pause).

**Window focus behavior:** When the window loses focus, ALL pollers pause, period. No exceptions. This is what lets macOS App Nap engage.

**Status bar telemetry indicator:**

Small indicator on the right side of the status bar (`Views/MainWindow.StatusBar.cs`). Three states, event-driven — updates only when the `BackgroundPollManager` fires a state-change event:

1. **Idle** — dim dot + "idle" label. Shows when no pollers are currently ticking (window unfocused, tab inactive, or nothing registered).
2. **Polling** — small colored dot (reuse `AccentBlue` or `AccentGreen`) + label showing which category ("Activity", "Trace"). If multiple pollers active, show the highest-cost one or just "polling".
3. **Long-running op** — different dot + label ("query running", "export 42%"). Optional — this overlaps with the existing elapsed-time tab title indicator, so skip it for now to avoid duplicate UI.

Do NOT make this indicator update on a timer. It listens to `BackgroundPollManager.StateChanged` events, which fire only on actual transitions (window focus, tab change, poller start/stop). A handful of events per session — no measurable cost.

The indicator doubles as a debug view: if the user reports energy issues, they can check the indicator while the window is backgrounded. If it says "polling" while unfocused, the focus gating layer broke.

**Files:**
- NEW: `Services/BackgroundPollManager.cs` — the manager
- `ViewModels/ActivityViewModel.cs` — replace `StartAutoRefresh` / `StopAutoRefresh` / `_autoRefreshTimer` with manager registration; `OnAutoRefreshEnabledChanged` calls `pollManager.SetPollerEnabled(...)` instead
- `ViewModels/TraceViewModel.cs` — replace `_counterTimer` with manager registration using the `pauseServerSideOnTabInactive: false` flag
- `Views/MainWindow.axaml.cs` — wire `Activated`/`Deactivated` → manager; hook into the main tab selection change (whatever event drives `Editor`/`History`/`Compare`/`Activity`/`Trace`/`Settings` switching) → manager
- `Views/MainWindow.StatusBar.cs` — add the indicator control, subscribe to `BackgroundPollManager.StateChanged`
- `Styles/AppTheme.axaml` + `AppThemeLight.axaml` — add `PollIdleBrush`, `PollActiveBrush` resources (DynamicResource per the #4 rule)

**Verification:**

- Turn on Auto-Refresh, leave Activity tab, switch to Editor. Status bar indicator → "idle" within one tick interval. Activity DMV queries stop firing (check via server-side trace or a log statement in `RefreshAsync`).
- Cmd+Tab away. Indicator → "idle". macOS Activity Monitor should show Lookout's energy impact drop to near zero within ~30 seconds (App Nap engaging).
- Cmd+Tab back, tap Activity tab. Immediate refresh fires (the catch-up). Then periodic ticks resume.
- Start a Trace, switch to Editor. Local UI counter stops updating. XE session on the server is still running (verify with `SELECT * FROM sys.dm_xe_sessions`). Switch back to Trace — counter catches up.

**Main risk:** Getting the catch-up-on-resume right without double-firing (one on resume, another when the periodic tick hits immediately after). Solution: on resume, fire the tick manually AND reset the DispatcherTimer's next-tick clock so it's one full interval from now.

### DONE: Task 2 — Option+Shift+Drag Crash + Column Selection as a New Feature

**What actually shipped, after significant course-correction.**

**First attempt (did not work):** Hypothesis was that our `UpdateOccurrenceHighlight` and `UpdateBracketHighlight` handlers were calling `TextView.Redraw()` on every caret/selection change during a rectangle-selection drag, racing with AvaloniaEdit's `SelectionLayer.Render()` and throwing `VisualLinesInvalidException`. CC added:

1. Guard both handlers to skip redraw when state hasn't changed (Part A)
2. Downgrade to per-line `TextView.Redraw(line)` for brackets (Part B)
3. Early-return if `Selection is RectangleSelection` at the top of both handlers (Part C)

Crash persisted identically. Four more crashes after deployment, same stack trace.

**The plot twist:** CC added diagnostic logging and discovered that Option+Shift+drag on macOS **never produces a `RectangleSelection` at all**. It produces ordinary `SimpleSelection` (or `EmptySelection`). AvaloniaEdit's modifier-based rectangle activation is broken on macOS Arm64 — the Alt modifier is functionally ignored by AvaloniaEdit's `SelectionMouseHandler`. So the RectangleSelection guard was a no-op, and the Part A/B guards helped with frequency but not with the race itself, because the race lives inside AvaloniaEdit's own render pipeline, not ours.

The crash stack has zero frames from our code. The exception fires asynchronously in a later composition frame, not during our `Redraw()` call. No amount of try/catch around our code can touch it.

**Actual fix that shipped:**

1. **Pointer-level block for Option+Shift+drag.** In `ConfigureEditor()`, added a `PointerMoved` handler on `SqlEditor.TextArea` with Tunnel routing that sets `e.Handled = true` when `KeyModifiers.Alt + KeyModifiers.Shift + left button pressed`. The gesture now does nothing instead of crashing. Cursor still places on click because only move events are blocked.

2. **Global `VisualLinesInvalidException` swallow in app-level exception handler.** Program.cs / App.axaml.cs filters this specific exception type from the `UnhandledException` path — logs to app.log at Warn level, does not produce a crash report. Insurance for any other code path that might hit the same upstream race.

**The bonus feature (newly implemented on top of the crash fix):**

Since Option+drag alone does nothing useful on macOS (AvaloniaEdit ignores the Alt modifier — the gesture just produces a regular contiguous selection, making it identical to click-then-shift-click), we claimed the gesture and implemented column/block selection from scratch. Three pointer handlers on `SqlEditor.TextArea` capture `PointerPressed` with Alt modifier, track the starting `TextViewPosition`, and on `PointerMoved` construct a `new RectangleSelection(TextArea, startPos, currentPos)` and assign it directly to `TextArea.Selection`. This bypasses AvaloniaEdit's broken modifier detection entirely. The `RectangleSelection` class itself works fine — only the activation gesture is broken upstream. Clipboard semantics (copy produces segmented text, paste produces rectangular paste) are free via AvaloniaEdit's built-in handling when `Selection` is a `RectangleSelection` instance.

Character-cell throttling prevents the race from re-emerging: updates only fire when the computed `TextViewPosition`'s (line, visualColumn) actually changes, not per pixel of mouse motion. `TextArea.Caret.BringCaretToView()` gives us auto-scroll during drag past the visible area.

**Shortcut added to `docs/SHORTCUTS.md`:** `Option+Drag — Column selection`.

**Lessons for future architecture work:**

- When a crash stack has zero frames from our code, treat "the library's internal race" as the leading hypothesis earlier than I did. I spent three rounds proposing fixes at our layer before CC's diagnostic logging revealed the modifier detection was broken at the library layer.
- Pointer-level gesture blocking (Tunnel + `e.Handled = true`) is a strong tool when we need to neutralize a buggy library behavior without modifying the library.
- When an upstream feature doesn't work, claiming the gesture and implementing it ourselves can be cheaper than fighting the library — 40 lines of code in our case.

### DONE: Task 5 — Removed Quick Execute (Shift+Click) Shortcut

**Unplanned, added late in session.**

After the pointer-level crash block landed in Task 2, the only remaining thing Shift+click in the editor did was fire the Quick Execute (prepare EXEC template) feature from v2.1.0. Testing revealed it was misfiring on non-sproc phrases — generating EXEC templates for arbitrary text. Decision to remove rather than fix:

- Misfires more than it helps (net-negative UX)
- Overloads Shift+Click, a universal "extend selection" gesture in every text editor including SSMS
- The right-click → Execute path on proc names already works correctly and knows when something is actually a proc
- Zero discoverability — no muscle memory formed across existing users after a year
- Reducing custom Shift/Alt pointer gestures on TextArea reduces future minefield surface

**What shipped:** Removed the Shift+Click binding. Right-click → Execute path verified still working. `docs/SHORTCUTS.md` updated.

### Task 2 had a long tail: Cmd+C after column selection

The column-selection gesture itself worked (as captured in the original Task 2 summary above). The problem surfaced later: Cmd+C immediately after an Option+drag column selection didn't copy — paste would return empty or stale clipboard content. Right-click → Copy always worked. So the selection was valid; the Cmd+C path was broken.

Several wrong hypotheses before the real root cause surfaced:

- KeyBinding on `TextArea.KeyBindings` preempts AvaloniaEdit's command routing — partially true, but the KeyBinding didn't fire reliably
- `ApplicationCommands.Copy` runs concurrently with our KeyBinding and races on the clipboard write — plausible given the 5/10 reliability we saw at one point, but didn't hold up under diagnostics
- Fire-and-forget async clipboard writes (`_ = SetTextAsync(...)`) losing the race to AvaloniaEdit's internal Copy — switching to `await` synchronously helped marginally but wasn't the fix

Fixes attempted and discarded along the way: reconstructing the `RectangleSelection` from stored `_columnSelectStart` / `_lastColumnSelectPos` at Cmd+C time and calling `SqlEditor.Copy()` (worked sometimes), switching to synchronous `RelayCommand` (still flaky), hooking `SelectionChanged` to capture positions regardless of which handler built the selection (didn't address the actual cause, though it was defensible as belt-and-suspenders).

The real root cause was **Avalonia's in-window `Menu` activating on Alt press**. Holding Option during an Option+drag puts the Menu into access-key-pending state — visible as the File menu header highlighting when Option is held. After the drag, the Menu's focus state interferes with Cmd+C reaching the TextArea's KeyBindings. Removing the underscore mnemonics from menu headers (`_File` → `File`) did not help — the Alt-activation behavior is separate from mnemonic character lookup.

The fix that worked: **route the Cmd+C column-copy through Window-level handling in `MainWindow.OnKeyDown`**, not TextArea-level KeyBindings. Window-level OnKeyDown fires regardless of Menu focus state.

Implementation shape:

- `QueryTabView.TryCopyColumnSelection()` — new public method that reconstructs the `RectangleSelection` from stored positions, calls `SqlEditor.Copy()`, returns `true` if a column selection was available to copy
- `MainWindow.OnKeyDown` (in `MainWindow.KeyBindings.cs`) — added an early Cmd/Ctrl+C case that checks `QueryEditorTab.IsChecked`, calls `TryCopyColumnSelection()` on the active tab via `QueryEditorHost`, marks handled if it returned true. Otherwise falls through — normal Cmd+C for SimpleSelection, results grid copy, etc., all unaffected
- TextArea-scoped Cmd+C and Ctrl+C KeyBindings removed from `QueryTabView.Editor.cs` — redundant now and were at risk of double-firing

### Latent issue to track

The Menu Alt-activation is still present. Any future editor gesture combining Alt with a keyboard follow-up will hit the same kind of interference. The Cmd+C workaround is targeted and works, but isn't structural. The real fix — if this pattern recurs — is disabling Avalonia `Menu`'s Alt-activation behavior globally, probably via attached property or class handler override. Not worth pursuing preemptively; flag it if it bites again.

### Lessons

- When a misbehavior's evidence has no frames from our code (crash stacks, failed KeyBindings), suspect library or platform layers earlier than intuition suggests. Demonstrated in the original Task 2 VisualLinesInvalidException crash; repeated in the Cmd+C saga, where the real interference was upstream of anything our code touched.
- Reactive fixes compound race conditions. Any time the proposed fix was "let the bad thing happen, then undo it," the outcome was flaky. The working fix moved the trigger point upstream (Window handler before Menu focus steals the gesture) rather than reacting downstream.
- Single-run success is not evidence of a fix working. "Worked the first time, didn't the next" was a recurring signal this session that the fix was addressing a symptom rather than a cause. When that pattern appears, the correct move is to stop fixing and add diagnostics.
- Test cleanliness matters more than we treated it. Ömer flagged his own test contamination (paste state lingering, fewer than 10 runs, Cmd+Tab timing); I should have pushed harder for strict protocols earlier instead of reasoning over noisy data.
