### DONE: Bug Fix — Single-Cell Paste Targets Wrong Column

**Status:** Fixed and verified. Native paste now works when a cell is actively being edited.

**The problem:** When you double-click a cell to edit it (e.g. DepartmentId column, row 5), then Ctrl+V to paste a value, the value lands in the FIRST column (EmployeeId) instead of the column you're editing. Both the custom selection system and the paste handler are involved.

**Root cause:** In `QueryTabView.EditMode.cs`, the `OnResultsGridKeyDown` method has a `Ctrl+V` handler that intercepts ALL paste events when in edit mode. It always calls `_viewModel.PasteRows(lines, startIndex)` which is the TSV row-paste feature (paste a full Excel row). The problem is it fires even when a cell's TextBox is focused for single-value editing. The native TextBox paste never gets a chance because `e.Handled = true` is set before the TextBox can process it.

**The fix:** Add an early-return check at the top of the `Ctrl+V` block. If a `TextBox` inside a `DataGridCell` currently has focus, do NOT set `e.Handled` and return immediately. The native TextBox paste will handle single-cell paste correctly. This is the exact same pattern the Escape handler already uses a few lines above:

```csharp
var focused = TopLevel.GetTopLevel(this)?.FocusManager?.GetFocusedElement();
if (focused is Avalonia.Controls.TextBox tb && tb.FindAncestorOfType<DataGridCell>() != null)
```

**Why this is safe:** The TSV row-paste (`PasteRows`) still works correctly for its use case. When you're in edit mode with row(s) selected but NOT actively editing a cell (no TextBox focused), the check doesn't trigger and `PasteRows` runs as before. The check only skips the handler when a cell TextBox has focus, which means you're doing single-cell editing and want native paste behavior.

**File:** `Views/QueryTabView.EditMode.cs` — inside `OnResultsGridKeyDown`, the `if (ctrl && e.Key == Key.V)` block (around line 170).

### DONE: Enhancement — Column-Aware TSV Paste (PasteRows)

**Status:** Fixed and verified. Grid-level paste now respects the selected/current column instead of always starting at column 0.

**The problem:** When you select a 2x2 range of cells in the middle of a grid (say columns 1-2, rows 1-2) and paste a 2x2 TSV block from Excel, the values land in columns 0-1 instead of columns 1-2. `PasteRows` always starts writing at column 0 regardless of what columns are selected.

**Root cause:** In `QueryTabViewModel.cs`, the `PasteRows` method only takes a `startIndex` (row) parameter. The inner loop always starts at column 0:

```csharp
for (int c = 0; c < cells.Length && c < colCount; c++)
    existing[c] = cells[c];
```

Meanwhile, the view-side Ctrl+C handler already knows the selected column range via `_dragStartColIndex` and `_dragEndColIndex` (the custom selection tracking fields from the v2.13.0 selection overhaul). But the Ctrl+V handler doesn't pass this info to `PasteRows`.

**The fix (two parts):**

1. **ViewModel** (`ViewModels/QueryTabViewModel.cs`): Add a `startCol` parameter to `PasteRows`:

```csharp
public void PasteRows(List<string[]> parsedRows, int startIndex, int startCol = 0)
```

Then offset the column index in the inner loop:

```csharp
for (int c = 0; c < cells.Length && (c + startCol) < colCount; c++)
    existing[c + startCol] = cells[c];
```

Same change for the "append new row" branch.

2. **View** (`Views/QueryTabView.EditMode.cs`): In the Ctrl+V handler, resolve `startCol` from the custom selection state. Use `Math.Min(_dragStartColIndex, _dragEndColIndex)` if both are >= 0, otherwise fall back to `ResultsGrid.CurrentColumn` index, otherwise 0. Pass it to `PasteRows`:

```csharp
int startCol = 0;
if (_dragStartColIndex >= 0 && _dragEndColIndex >= 0)
    startCol = Math.Min(_dragStartColIndex, _dragEndColIndex);
else if (ResultsGrid.CurrentColumn != null)
    startCol = ResultsGrid.Columns.IndexOf(ResultsGrid.CurrentColumn);

_viewModel.PasteRows(lines, startIndex, startCol);
```

**Why this matters:** Copy already respects column selection (Ctrl+C copies only the selected column range). Paste should mirror that behavior. If you copy 2 columns from Excel and paste onto a 2-column selection, the values should land in those columns, not columns 0-1.

**Files:**
- `ViewModels/QueryTabViewModel.cs` — `PasteRows` method
- `Views/QueryTabView.EditMode.cs` — `Ctrl+V` block in `OnResultsGridKeyDown`

### Feature: Paste On Read-Only Cell Should Auto-Enter Edit Mode

**The problem:** In the results grid, if a cell is selected but the grid is still in read-only mode, pressing Cmd/Ctrl+V does not naturally paste into that cell. Now that edit-mode paste is fixed, the next logical UX step is letting paste from a focused read-only cell automatically enter edit mode and apply the paste at that same location.

**Desired behavior:**

1. If the **results grid** has focus, the current result is **edit-eligible**, and the user presses Cmd/Ctrl+V while **not already in edit mode**, the app should auto-enter edit mode and then paste.
2. If a single cell is selected, the paste should target that exact cell.
3. If a rectangular selection exists, the paste should start at the **top-left** selected cell.
4. If full-row selection mode is active, the paste should start at **column 0** of the top selected row.
5. If the result is **not edit-eligible** (no PK, unsupported query shape, stacked results, etc.), do not auto-enter edit mode. Optionally show a short transient status message like "Result is not editable".
6. This behavior must only apply when the **results grid** has focus. It must not trigger when the SQL editor has focus.
7. Once edit mode is entered, the existing paste rules from the first two tasks must still hold:
   - active cell editor -> native paste
   - grid-level paste -> top-left of selection, otherwise current cell

**Implementation shape:**

1. Capture the paste anchor **before** entering edit mode:
   - selected/current row
   - selected/current column
   - full-row selection state
   - rectangular selection state, if present
2. Enter edit mode.
3. After the `ItemsSource` swap settles, restore the anchor selection/current column.
4. Reuse the existing grid-level paste path instead of creating a second paste implementation.

**Main risk:** Entering edit mode swaps the grid source, so row/column focus and selection can be lost if the anchor is not captured and restored explicitly before paste runs.

**Likely files:**
- `Views/QueryTabView.EditMode.cs`
- `ViewModels/QueryTabViewModel.cs` (only if the existing paste helper needs a small extension)

### Task 4: Normalize Query Execution Feedback

**The problem:** Query execution feedback exists today, but it is split across too many channels and the semantics are inconsistent. SQL Server messages are collected, but the app still has to decide what counts as success, row count, returned rows, DDL completion, warning, cancellation, and partial failure. This makes some cases feel under-reported even when the raw data was actually captured.

**Current state (what already works):**

- `SqlConnection.InfoMessage` is captured before `OpenAsync`, so server informational output is already collected.
- `StatementCompleted` is used for DML row counts.
- SQL exceptions are expanded from `SqlException.Errors` and surfaced with line numbers.
- Pure DDL with no result sets and no row counts already gets a `"Commands completed successfully."` message.
- The Messages tab is auto-opened for no-result executions, so DDL feedback is not missing from the backend.

**What is still wrong:**

1. The app mixes **raw SQL Server messages** with **derived UI summaries**.
2. `SELECT` results are represented in Messages as `"(N row(s) affected)"`, which blurs **rows returned** vs **rows affected**.
3. `InfoMessage` traffic is treated as one generic bucket, so `PRINT`, low-severity `RAISERROR`, and other informational messages are not distinguished.
4. The durable query status can be weaker than the transient flash. For example, plain DDL success may end up showing only elapsed time in the query status area even though `"Commands completed successfully."` was captured.
5. Feedback policy currently lives partly in `DatabaseService` and partly in `QueryTabViewModel`, so every new query outcome risks adding more ad-hoc logic.

**The goal:** Introduce a small, explicit execution feedback model that becomes the single source of truth for query outcome semantics.

**Proposed model:**

Create a lightweight summary object produced by `DatabaseService` for every execution. Example shape:

```csharp
public class ExecutionSummary
{
    public ExecutionOutcome Outcome { get; set; } // Success, PartialSuccess, Error, Cancelled
    public int ResultSetCount { get; set; }
    public int RowsReturned { get; set; }
    public int RowsAffected { get; set; }
    public int ErrorCount { get; set; }
    public int WarningCount { get; set; }
    public int InfoCount { get; set; }
    public long ExecutionTimeMs { get; set; }
    public string PrimaryStatusText { get; set; } = "";
    public string PrimaryFlashText { get; set; } = "";
}
```

This does **not** replace raw `QueryMessage` entries. It sits above them and gives the UI one canonical interpretation of the execution.

**Behavior policy by query type:**

1. **SELECT only**
   - Messages may include timing and server info.
   - Summary should report:
     - `ResultSetCount`
     - `RowsReturned`
     - status like `"1 result set, 125 rows"`
   - Do **not** label returned rows as `"row(s) affected"` in the summary layer.

2. **INSERT / UPDATE / DELETE / MERGE**
   - Use `StatementCompleted` row counts.
   - Summary should report:
     - `RowsAffected`
     - status like `"3 row(s) affected"`

3. **DDL only** (`ALTER PROC`, `CREATE VIEW`, `DROP INDEX`, etc.)
   - If no errors and no result sets:
     - summary should explicitly say `"Commands completed successfully."`
   - Query status should preserve that message in a durable way, not only as a transient flash.

4. **Mixed batches**
   - Example: `UPDATE ...; SELECT ...; PRINT ...`
   - Summary should report the dominant execution shape clearly:
     - both `RowsAffected` and `RowsReturned` if both happened
     - outcome still `Success` unless a later statement errors

5. **Partial success with later error**
   - Example: first statement succeeds, second fails
   - Outcome should be `PartialSuccess` or `Error` with preserved success-side row counts/messages
   - UI should not collapse everything into a generic `"Error"` and lose the fact that earlier statements did complete

6. **Cancellation**
   - Outcome should be `Cancelled`
   - status and flash should say so explicitly

7. **Server info / PRINT / low-severity messages**
   - Keep raw messages
   - Ideally distinguish at least:
     - `Print`
     - `Info`
     - `Warning`
   - If not immediately possible, leave raw collection as-is for now, but do not let it block the summary model

**Implementation approach:**

1. Keep collecting raw `QueryMessage` items as today.
2. Add `ExecutionSummary` to `QueryExecutionResult`.
3. Build the summary in `DatabaseService` once, after execution completes.
4. Update `QueryTabViewModel` to consume `ExecutionSummary` instead of re-deriving meaning from:
   - `Results`
   - `TotalRowsAffected`
   - ad-hoc message inspection
5. Use the summary to drive:
   - `StatusText`
   - `QueryStatusText`
   - transient flash text/severity

**Important constraint:** This should be a semantic cleanup, not a UX redesign. Keep the current Messages tab and result tabs. The goal is to make feedback **more reliable and easier to reason about**, not to rebuild the UI.

**Likely files:**
- `Services/DatabaseService.cs`
- `Models/QueryMessage.cs` or a new dedicated model file for `ExecutionSummary`
- `ViewModels/QueryTabViewModel.cs`

### Task 5: Stacked Results Layout And Resizing Overhaul

**The problem:** Multi-result queries currently render as stacked DataGrids, but the layout feels heavier and less polished than the single-result view. Each result set gets a large header section, the visual separation is clunky, and resizing the overall results panel causes all stacked grids to expand/shrink together in a way that hurts readability.

**Symptoms observed:**

1. The stacked-result headers are visually too tall/heavy compared to the compact single-result tab layout.
2. Multiple result sets read like one fragmented grid instead of clearly separated but compact sections.
3. Dragging the main editor/results splitter resizes the entire stacked-results area proportionally, so all result grids grow/shrink together.
4. Small result sets waste space; large result sets can dominate; overall balance feels unstable.

**Desired behavior:**

1. Stacked results should feel visually **closer to the single-result presentation**:
   - compact headers
   - tighter spacing
   - less card-like bulk
2. Each result set should still be clearly identifiable:
   - result number
   - row count
   - pin/copy actions if still needed
3. Small result sets should stay compact.
4. Large result sets should get a bounded viewport with their own internal scrolling.
5. Resizing the main results panel should change the **overall available space**, but should not awkwardly re-proportion every child grid by row-count math.
6. A multi-result layout should remain readable whether there are:
   - 2 result sets
   - many result sets
   - a mix of tiny and large result sets

**Strong recommendation:** Prefer a compact vertical list of independently sized result sections over star-weighted row definitions that redistribute height across every result set.

**Suggested layout policy:**

1. For each result set:
   - compact header row
   - DataGrid below it
2. Grid height rules:
   - empty/small result sets: auto or near-auto height
   - medium/large result sets: capped height
   - internal scrolling inside each grid once cap is reached
3. Avoid making all result grids share proportional `Star` sizing based on row count.
4. If splitters between stacked result sets remain, they should resize **that section**, not create global weirdness.
5. The outer editor/results splitter should only control the height of the overall results region.

**Visual direction:**

1. Match the compactness of the single-result view as much as possible.
2. Reduce header padding/height.
3. Keep actions subtle and lightweight.
4. Improve separation using thin borders/background contrast, not oversized section chrome.

**Main implementation risk:** The current stacked-results builder appears to use dynamic row definitions weighted by row count. That makes the math easy but the UX poor. Reworking this may require changing the container strategy, not just tweaking padding.

**Likely files:**
- `Views/QueryTabView.Results.cs`
- possibly `Views/QueryTabView.axaml` if any supporting container/style changes are needed
